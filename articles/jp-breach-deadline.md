個人情報の漏えい等が起きたときの、個人情報保護委員会への報告（速報・確報）の期限を計算する小さなライブラリと CLI を公開しました。依存パッケージなし、Node.js 18 以上、MIT です。

https://github.com/Radineer/jp-breach-deadline

```
$ npx github:Radineer/jp-breach-deadline 2026-10-05
事態を知った日: 2026-10-05
速報: 2026-10-08〜2026-10-10 が目安
確報: 2026-11-04 まで（知った日から30日以内）
  2026-11-03 は文化の日のため翌日へ
```

## 仕様の出どころ

仕様はすべて一次資料から取りました。2026-10-28 に原文を確認しています。

- 個人情報の保護に関する法律施行規則 第7条・第8条（e-Gov 法令 API、法令ID 428M60020000003、2026-06-14 施行の版）
- 個人情報保護委員会「個人情報の保護に関する法律についてのガイドライン（通則編）」3-5-3-3（速報）・3-5-3-4（確報）

| 項目 | 決まり |
|---|---|
| 報告対象 | 第7条1〜4号（要配慮個人情報／財産的被害のおそれ／不正の目的によるおそれ／本人千人超）のどれか |
| 速報 | 知った後、速やかに。目安は知った時点から概ね3〜5日以内 |
| 確報 | 知った日から30日以内。第7条第3号の事態は60日以内 |
| 起算 | 知った日を1日目とし、土日・祝日も含めて数える |
| 末日 | 30日目・60日目が土日・祝日・年末年始閉庁日（12/29〜1/3）なら翌日 |

民法の期間計算（初日不算入）とは逆で、ガイドラインは知った日を1日目にすると明記しています。ここを取り違えると、期限が1日ずれます。

## 実装で気をつけたこと

### 日付は UTC の暦日だけで扱う

入力は `YYYY-MM-DD` の暦日だけにして、`Date.UTC` で作った日付に日数を足しています。ローカルのタイムゾーンや夏時間に影響されないようにするためです。`2026-02-30` のような存在しない日付は、`Date` が勝手に繰り上げる前に弾きます。

```js
const [y, m, d] = ymd.split('-').map(Number);
const t = new Date(Date.UTC(y, m - 1, d));
if (t.getUTCMonth() !== m - 1 || t.getUTCDate() !== d) throw new RangeError(`存在しない日付です: ${ymd}`);
```

### 末日の繰り延べは、当たらない日まで送る

ガイドラインの文言は「その翌日を報告期限とする」です。土曜が末日なら翌日の日曜もまた休みなので、当たらない日まで送っています。ここは文言をこのライブラリが解釈した部分なので、README にもそう書いています。年末年始に掛かると、12/30 から 1/4 まで5日送られます。

### 祝日は内閣府の CSV から作り、範囲外は止める

祝日は内閣府「国民の祝日について」の CSV（Shift_JIS）を UTF-8 に変換し、JSON にして同梱しています。データの無い年を渡すと、祝日を見ずに黙って計算するのではなく、エラーで止めます。期限の道具が静かに間違えるのがいちばん困るからです。

## 試験

`node --test` で7件です。祝日をまたぐ例（10/5 → 11/3 文化の日 → 11/4）、60日で日曜に当たる例（10/1 → 11/29 → 11/30）、年末年始をまたぐ例（12/1 → 12/30 → 2027/1/4）、入力の誤り、データの無い年を入れています。

## 自社の道具で同じ間違いをしていた

社内で使っている「漏えい対応クロック」でも同じ期限を出していましたが、原文と照らすと次の3点がずれていました。

- 確報の期限を「知った時刻 + 30 × 24 時間」で出していた（1日目の数え方が違い、約1日遅い）
- 土日・祝日・年末年始の繰り延べが無かった
- 第7条第3号の60日に対応していなかった

このライブラリと同じ計算に直して、10月28日に公開し直しました。期限の計算を表計算や自前のコードでしている場合は、上の試験の例で一度確かめてみてください。

## 注意

期限の計算の道具で、法的な助言ではありません。報告の要否や「知った」時点（法人ではいずれかの部署が知った時点）は事業者が判断します。
